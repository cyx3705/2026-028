# cs/ —— 微信剪贴板桥（C# / .NET Framework）

**零依赖、零安装、零构建工具。** 用每个 Windows 都自带的 C# 编译器编译。

```
chat.html ──WebSocket──▶ bridge.exe ──剪贴板＋键盘──▶ 微信当前对话
                              ▲
                              └── 剪贴板监听 ◀── 你在微信里 Ctrl+C
```

## 用法

```cmd
start.bat
```

会自动编译（如果还没编译过）并启动。

桥**不托管页面**：页面用 `file://` 直接打开就能连 `ws://127.0.0.1:8765/ws`。

**发送**：页面里打字 → 点发送 → 桥把密文写进剪贴板、把微信切到前台、`Ctrl+V` `Enter`。
**发送目标 = 微信中当前打开的那个对话**，桥不选对话，所以发之前在微信里切好即可。

**接收**：默认 `--read=mem`，直接读微信进程内存里的消息页（见下）。
老路 `--read=clip` 仍在：在微信里选中消息 `Ctrl+C` → 桥发现剪贴板变化 → 推给页面。

### HTTP 端点

| 端点 | 作用 |
|---|---|
| `GET /status` | 微信窗口状态、pid、登录态、尺寸、是否有前台、自动拉取开关、上次拉取结果、客户端数 |
| `GET /pull` | **拉取当前对话里看得见的消息**（拖选 + Ctrl+C），返回纯文本。见下 |
| `GET /shot` | 微信窗口截图 PNG（**验收用**：桥说自己成功不算数，得看截图） |
| `GET /wincheck?hwnd=<十进制句柄>` | 对任意窗口跑一遍"是否已登录"的判据，调试用 |
| `WS /ws` | 页面通道。收 `{"type":"send","text":…}` / `{"type":"status"}` / `{"type":"pull"}` / `{"type":"autopull","on":true\|false}` |
| `WS` 推给页面 | `hello` / `status` / `pulling` / `pulled`（自动拉取时带 `"auto":true`）/ `autoPull` / `clipboard` |

页面走 **WS 的 `{"type":"pull"}`** 而不是 HTTP 的 `/pull`：`file://` 页面用 `fetch`
打本地端口有 CORS 和本地网络访问（LNA）的风险，而 WS 从 `file://` 连回环地址早就验证可用。

## 接收消息：mem 模式（直接读微信进程内存）

拖拽 + `Ctrl+C` 那条路还在（`--read=clip`），但它要抢前台、动鼠标，限制太大。
现在默认 `--read=mem`：**只 `ReadProcessMemory` 读微信自己的进程**，不碰鼠标、
不碰剪贴板、不抢焦点、不要数据库密钥、不爆破密码。

### 数据在哪

```
C:\Users\<用户>\Documents\xwechat_files\<wxid>_<n>\db_storage\
    message\message_0.db        会话消息（85 张 Msg_<md5> 表）
    message\biz_message_0.db    另一批消息（79 张 Msg_<md5> 表）
    session\session.db          SessionTable：会话行（含 summary / last_timestamp）
    contact\contact.db          联系人
```

* 表名 = `Msg_` + `md5(session_id)`，**不是** md5(wxid) 之外的东西：
  `filehelper`→`9e20f478…`、`wxid_pno349onlek322`→`2ba0e1d0…`。
* `Msg_` 一行 17 列，`2=local_type`（1 文本 / 3 图片 / 34 语音 / 43 视频 / 49 链接 /
  10000 系统），`5=create_time`，`12=message_content`（文本就是明文 UTF-8）。
  注意 `local_type` 有合成值（实测 `244813135921` = `57<<32 | 49`），不是解析错。
* 库里**全部 `.db` 都是 SQLCipher 4 加密的**，只有 `key_info.db` 不是。
  密钥拿不到：4.1.11+ 不再在内存里留 `x'<hex>'`；整块内存按 8 字节对齐做 AES
  判据（3700 万个候选、235 秒）零命中。**不要去爆破口令**：PBKDF2-HMAC-SHA512
  256000 轮单次 170 ms，8 字节对齐空间要 1748 小时（32 核也要 54 小时）。

### 办法：页缓存里是明文

SQLCipher 把每一页解密进 SQLite 的页缓存，所以**明文页就在堆里**。pcache1 的
`PgHdr1`（x64）版式：

| 偏移 | 含义 |
| --- | --- |
| +0 | `pBuf` → 4096 字节页数据 |
| +16 | `iKey` u32 = 页号 |
| +24 | `pNext`（哈希链） |
| +32 | `pCache` → 标识是哪个 pager |
| +40 / +48 | `pLruNext` / `pLruPrev` |

第 1 页的 b-tree 头在偏移 100，其它页在 0。同一个库微信开了好几个连接，**每个连接
一份页缓存、一份修订版**；会话表实测不同修订版能读到的会话数不一样（53 / 73 / 153）。

### 四个必须记住的坑

1. **`change counter` 不能当"新鲜度"**。同一个 `message_0.db` 的页缓存里同时有
   `cc=3639721513`（1881 页）和 `cc=1166134073`（1883 页）两份；按 cc 挑"最新"
   会挑到**旧**的那份（那份里会话停在 17:14、消息表一行没有），新数据在后一份里。
   page 1 只是那个连接自己缓存里的老副本。**会话行按 `last_timestamp` 取最大、
   消息按 `local_id` 合并取最新**，别信 cc。
2. **最新写入的页不在任何页缓存里**。内存里"长得像页"的缓冲约 24 万个，只有
   约 4000 个落在 `PgHdr1` 页缓存里；新写的页只以零散页映像的形式留在别处，
   用 `PgHdr1` 那套枚举永远看不见。**这就是"打开的对话读不出来"的直接原因**：
   页缓存里那份 TT 的消息停在前一天、甚至 0 行。
3. **内部页的单元指针数组从 +12 开始**（头部 +8 是 4 字节"最右孩子"指针），
   叶子页才是 +8。原来统一按 +8 读，内部页的子页指针全错位四字节，走全树会读错页。
4. **认页要严**。同一段小 rowid（比如 206–216）在很多表里都存在，按"rowid 接得上"
   放宽到 200 就会把文件传输助手的页认成群聊的。

### 严格页校验 + FreshTail

`MemPageIndex` 用**严格页校验**在整块内存里认出真的页映像（不看 `PgHdr1`）：
单元指针必须全部落在 `[cellstart, 4096)` 内、互不相同，而且最小值正好等于
`cellstart`（SQLite 从 cellstart 往上连续堆放单元）。随机数据几乎不可能同时满足，
于是"不在页缓存里"的新页也能捞出来。

`FreshTail(table)` 取最新几行：

1. 拿页缓存里根页的孩子集合；
2. 在内存页映像里找**孩子集合重合最多、最右 key 最大**的内部页 —— 那就是根页的新副本
   （实测 TT 的根页 377：孩子 283→286，最右孩子 1883→1888）；
3. 它最右单元给出 `(孩子页号, 该子树最大 rowid)`，按页号直接读最稳；
4. 页号不在缓存里时，才按 rowid 去页映像里认叶子页，且要求
   **rowid 严格接得上（≤20）且比页缓存里的更新**。

### 代价与覆盖

* 一次抓取 ≈ 0.55 s（约 400 MB / 900 个区域），页索引 ≈ 0.3 s，一次自动轮询 ≈ 1 s。
* 轮询触发：`db_storage\*\*.db-wal` 的长度或 mtime 一变就去读一次（微信写库才动它）。
* 覆盖**取决于根页在不在页缓存里**：实测未绑定时只有 3/173 张表读得出内容；
  但**你正在看的那个对话，它的根页就在缓存里** —— 所以"绑定当前打开的对话"这条路
  现在能读实时消息（TT 从 0 行变 39 行，含最新 22:43 的消息）。

### 会话选择：按"最新消息"列 3–5 个

页面「🔗 选择会话」弹出的列表**以最新消息为准**，每条用时间 + 对方 + 正文当身份。
桥那边两条路并用：

1. 会话行的 `username` 直接算出表名 `Msg_` + `md5(wxid)` —— 实测 73 个会话里
   55 个对得上（对不上的 18 个正是 `gh_*` / `@openim` / `brandsessionholder`
   这类噪声，已排除）；
2. 会话行还带 `last_msg_locald_id` + `last_timestamp`，拿这两个去内存页映像里
   按 rowid 认那一页就能读到最新那条 —— **不需要表的根页在页缓存里**。

读不到正文就回落成会话摘要；最新那条是卡片/图片时拿它前面最近一条有正文的当提示。
绑定优先给 `session`（wxid）而不是表名：桥能算出表名，还能在根页缺失时用
`last_msg_locald_id` 当锚点走 `LeafChain`（叶子页的 rowid 区间严丝合缝铺满，
所以"下一页 = 最小 rowid 接上一页最大 rowid"能一路串下去）。

### 版本依赖：哪些地方会随微信版本变

这套读法是**中等强度依赖版本**（实测 4.1.13.65）。按"变了会怎样"排：

| 依赖的东西 | 变了会怎样 | 能不能自己发现 |
| --- | --- | --- |
| 页大小 4096 / 保留区 80 | 页解析全错，一行都读不到 | **能**：诊断里拿页 1 的 16/20 字节核对，对不上直接写"← 对不上" |
| `Msg_` 17 列、`SessionTable` 列序、`Name2Id` | 列取错或取不到 | 半能：列数对不上就丢掉那行（不会崩），诊断显示"消息表 N 张、能读到 M 张" |
| `Msg_<md5(session_id)>` 表名规则 | 认不出会话 | 半能：`wxread match` 直接核对"会话行算出的表名对不对得上真表" |
| pcache1 `PgHdr1` 偏移（+0 pBuf / +16 iKey / +32 pCache） | 页缓存枚举全空，只剩严格页那条路 | **能**：诊断里"严格页 0 张"就说明两条路都没了 |
| SQLite 文件格式（b-tree 头、单元指针） | 严格页校验直接不通过 | 能：文件格式 3 十几年没动，这条最稳 |

好消息是**不用密钥**这件事跟版本无关，而且失败是"读不到"，不是"读错"或者崩溃。
坏消息是最坏情况下要靠诊断里的数字人工判断，所以**页面的「🩺 诊断」要能拿到**。

### 自己发的不算收到的

`Msg_` 行里 `origin_source`：**1 = 本机发出**，2 = 从服务器收到。绑定会话之后，
`origin_source == 1` 的行直接跳过 —— 否则页面刚发出去的密文会被自己读回来、
当成对方发来的，E2E 那层（计数器/重放）会出一串看不懂的怪事。页面这边还有
一道：发出去时记下正文，读回来一模一样就丢掉（"回声"），只留最近 20 条。

**判据刻意不取 `sender == 我的 id`**：从手机发出的消息也带着我的 id，而那条
是"对面视角发来的"（文件传输助手的回路测试就是靠它），不能一起滤掉。

### 诊断工具

`cs/wxread.exe`（`wxread.cs` + `wxdb.cs` 编译，不入库）：

```cmd
wxread dbs                  列出恢复出来的库
wxread sessions             会话（跨修订版取最新）
wxread msgs <sessionId>     某个会话的消息
wxread fresh                每张消息表能读到的最新时间
wxread pagers / pagescan    页缓存清单 / 全内存页形状扫描
wxread page <页号>          某个页在各个修订版里的样子
wxread find <文字>          在内存里找一段文字落在哪一页
wxread leaf|probe <表名>    根页、最右叶子、新根页副本
```

输出是 UTF-16，`Get-Content` 直接看会乱；重定向后按 UTF-16 解码再读。

## 独立探针

不必开浏览器就能跟桥说话：

```cmd
python wsprobe.py --status          REM 安全探针：不碰微信、一个键都不按
python wsprobe.py --send "内容"      REM 真发一条到微信当前对话
```

`--status` 是刻意分开的：`send` 最终会调 `SendToWeChat()`（动剪贴板 + 发按键），
而 `status` 走完全独立的查询分支。所以

- `status` 有回执、`send` 超时 → WebSocket 线程活着，卡在发送里面
- `status` 也没回执 → 整个通道死了

**注意**：别在 PowerShell 里自己拼 JSON 传参——PS 5.1 会把参数里的双引号吃掉，
`{"type":"send"}` 变成 `{type:send}`，桥的 `JavaScriptSerializer` 直接报
`无效的 JSON 基元`，表现是"桥不回话"，很容易误判成桥坏了。

## 安全护栏

发按键是**盲发**，这是整个方案最危险的地方。所以有三道闸：

1. **激活**：`AttachThreadInput` + `SetForegroundWindow` 把微信切到前台
2. **校验**：检查前台窗口**确实是微信进程**，且 class 名含 `Qt`
3. **登录态**：窗口尺寸和样式必须像已登录主界面

**任一校验失败 → 直接中止，一个按键都不发**，并向页面返回
`error: 无法把微信窗口切到前台，已中止（按键未发送）` 之类的具体原因。

### 第 3 道闸的判据（实测数据）

**踩过的坑**：微信被手机端顶下线、PC 弹着登录二维码时，前两道闸照样通过
（同一个 pid、同一个 Qt 窗口类），结果密文被粘进二维码窗口，**桥还报告 `ok`**。

| | 尺寸 | 可缩放 |
|---|---|---|
| 登录二维码界面 | 295×387 | ❌ 固定 |
| 已登录主界面 | 1017×690 / 1721×1041 | ✅ 有 `WS_THICKFRAME` |

### ⚠️ 已知风险

- **粘贴目标取决于微信内部哪个输入框有焦点。**
  如果微信没打开对话、或焦点停在「搜索」框，密文会粘到奇怪的地方。
  桥无法区分——**UIA 读不到微信内部结构**（见下）。
- **校验与发键之间有约 80ms 窗口期**，理论上焦点可能被抢走。风险很低，但不是零。
- 桥只监听 `127.0.0.1`，没做鉴权。本机自用没问题，暴露到局域网前必须加 token。

## 拉取消息：怎么从微信里把消息读出来

**微信的消息区是一整块自绘画布**，UIA 完全读不到 —— 连开了无障碍桥也只有 1 个元素
（设上 `SPI_GETSCREENREADER` 并重启微信后重探，结果一样）。键盘也没有"全选消息"这个命令
（8 种挪焦点的办法全部零变化）。

**能走通的只有一条**：用鼠标在消息区**拖一下**形成一次文字选择，再 `Ctrl+C`，
微信就把选中的消息以纯文本放进剪贴板：

```
Pinavia
2026年09月18日 17:17
E2E1-K.BDSEQpqu…
（空行）
Pinavia
2026年09月18日 17:18
123123
```

`PullMessages()` 做的就是这件事：切前台 → 沿右侧头像列拖一个**细长方形** → `Ctrl+C` → 读剪贴板。
四道安全闸（前台、已登录、拖拽起终点像素属于微信），任一不过就一个键都不按。

**用拖拽而不是点击**：拖动过程中不会触发消息里的链接，所以即使起点落在某条消息上也安全。

### ⚠️ 必须拖成"细长方形"，拖一条竖线是错的

这一条是后来纠正的，而且**纠正之前它一直在悄悄读旧剪贴板**：

| 拖法 | 剪贴板序号 | 结论 |
| --- | --- | --- |
| 零宽度的竖线 `x = right-51` | **两次都没变** | 什么都没选中；读到的是上一次留在剪贴板里的内容 |
| 细长方形 `right-30 → right-70` | 每次都变（FRESH） | 正确，可重复 |

竖线的失败是**静默**的：`DragAndCopy()` 只在"序号变了"时才算成功，但早期版本里
竖线偶尔也能选上，于是留下了"拉取成功"的假象。判断依据不能只看"剪贴板里有没有东西"，
必须看**序号有没有变**。探针（`probe.exe fine`）就是按这个原则对比的。

`x` 取 `30..70`：实测这个窗口里自己的头像列在距右边缘 `31..66 px`，气泡文字右缘在 `79 px`，
所以 `30..70` 正好盖住头像列、压不到文字 —— 也就是"沿右侧头像处拖"。

### 坐标不能按窗口比例算

左侧图标栏和会话列表是**固定像素宽**（约 390px），按比例在窄窗口下会掉进会话列表里 ——
窗口宽 800 时 `0.40 × 800 = 320px`，已经在会话列表上了。所以从**右/下边缘**算固定内缩：

```
x 外 = 右边缘 - 30      起点，落在头像右缘
x 内 = 右边缘 - 70      终点，落在气泡右缘
yBot = 下边缘 - 110     起点：输入框正上方，就是"最下面"
yTop = yBot - 300       终点：只往上拉 300px（并且离顶至少 120px）
```

### 不能拉到顶：会把会话列表翻上去

早先是 `yTop = 上边缘 + 70`，等于顶着标题栏往上拖。**微信会因此自动把列表往上翻**，
翻到很久以前 —— 于是每次拉到的都是不同的一屏（同一套代码实测一会儿 866 字符一会儿
1320 字符），而且把用户正在看的对话位置也带跑了。

改成贴着底部往上拉一段就稳了。实测（连拉两次不重置，看第一条是不是同一个）：

| 高度 | 条数 | 两次第一条 |
| --- | --- | --- |
| 300 | 4 | ✅ 完全一样 |
| 420 | 6 | ✅ 完全一样 |
| 560 | 7 | ✅ 完全一样 |

取最小的 **300**：页面只处理最近 5 条，信息越少越不容易出事，也越不打扰。

窗口**移动**不受影响：每次重新 `GetWindowRect`，`SetCursorPos` 用的是绝对屏幕坐标
（实测在 `(-2471, 292)` 这种负坐标的第二显示器上照常工作）。

输入框高度随草稿行数变，所以底部内缩有兜底：万一拖进了输入框（把草稿选中了），
结果里不会有"年月日"那行，`LooksLikeDump()` 判定不过就加大内缩重试。

### 第四道闸：拖之前先问"这个像素是谁的"

鼠标拖拽是按**屏幕坐标**打到最上面那个窗口的。踩过：微信不是最前面那个窗口时，
光标底下其实是 Solid Edge，一拖就在别人的模型上拉了个框。

所以 `PixelBelongsToWeChat()` 用 `WindowFromPoint` 查起终点的归属进程，
不是微信就一个键都不按：

```
拉取中止: 像素(1524,967)属于 hwnd=… pid=… class=… ，不是微信
```

### 不打扰用户的三件事

拉取必然要把微信切到前台（要真的鼠标和 `Ctrl+C`），但做完之后桥会还回去：

1. **光标**：`GetCursorPos` 存一份，`finally` 里 `SetCursorPos` 放回原处。
2. **前台窗口**：拉完 `SetForegroundWindow` 还给用户原来那个窗口（`RestoreForeground`）。
3. **剪贴板**：自动拉取会先把用户原来的剪贴板内容读出来，拉完再写回去。
   只在"剪贴板里还是我们刚放进去的东西"时才还原，避免踩掉用户此刻的复制。

### 自动拉取：等微信自己切到前台

**微信 4.x 收到消息不走 Windows 通知中心，也不弹 toast 窗口** —— 实测全程没有任何新顶层窗口，
它就是直接把自己的主窗口激活到前台。所以能挂钩子的信号只有
`EVENT_SYSTEM_FOREGROUND` 打在自己的窗口上：

```
18:05:12 HOOK ev=0x0003 pid=19576 hwnd=263490 class=Qt51514QWindowIcon title=微信
18:05:13 FG wechat foreground=True
```

好处是"自动拉取"并不额外抢焦点 —— 微信已经先抢了。`AutoPullLoop()` 挂这个钩子，
排队、去抖（2.5 秒一次）、等 500ms 让消息渲染出来，再拉。

**两个坑，都踩过：**

1. **`SetWinEventHook` 的回调委托必须被静态字段引用住。**
   钩子只拿走一个函数指针，托管侧那个隐式生成的委托没人引用，一次 GC 之后就被回收，
   **钩子从此再也不回调，而且不报任何错**。症状极有迷惑性：启动后触发过一次，之后彻底安静。
   现在用 `private static readonly WinEventProc _foregroundHookProc = WeChatForegroundHook;` 钉住。

2. **`WINEVENT_OUTOFCONTEXT` 的钩子是靠"安装钩子那个线程"的消息队列投递的。**
   第一版等待循环里只有 `Thread.Sleep`，没有抽消息，结果一个事件都收不到。
   必须 `PeekMessage` + `TranslateMessage` + `DispatchMessage`。

自锁：拉取本身会把微信切到前台，那也触发这个事件，所以拉取前后各安静一段时间，
不然会自己触发自己。

### 拉取期间必须屏蔽剪贴板推送

拉取用的那一下 `Ctrl+C` 会被剪贴板监听线程也捕获到。`_lastSentSeq` 是**按完之后**才写的，
监听线程 400ms 一轮，完全来得及在那之前把这次变化抓走（日志里实测抓到了）。

手动拉取时页面用 `pullingUntil` 挡得住，但**自动拉取不是页面发起的**，页面不知道，
于是同一条消息会被处理两遍（`clipboard` + `pulled`）。所以 `_suppressClipboardUntil` 这道闸
必须在桥这边，覆盖整个"拖选 + Ctrl+C + 还原剪贴板"的过程。

### 为什么"不抢鼠标"做不到（四条路都试过）

拖选必须动真实鼠标：`SendInput` 是按屏幕坐标打真实硬件输入的，系统光标一定会跟过去。
（现在拖完会把光标放回原处，所以只是闪一下。）为了彻底不碰光标，试了四条路，全部失败：

| 方法 | 结果 |
| --- | --- |
| `PostMessage` / `SendMessage` 发 `WM_LBUTTONDOWN/MOUSEMOVE/UP` | 微信完全不理。Post 和 Send **都是 STALE**（剪贴板序号没变），和 Qt 官方论坛/StackOverflow 记录的一致：Qt 窗口不响应合成的鼠标消息 |
| 旧版 `InjectTouchInput`（Windows 自带触摸注入） | `InitializeTouchInjection()` **免管理员就成功**，但 `InjectTouchInput()` **永远 `err=87 ERROR_INVALID_PARAMETER`**。8 种参数组合、3 种 feedback 模式、以及**手写清零缓冲按显式偏移填字段**（排除结构体/padding 疑问）全部一样 → 是 API 层拒绝，不是数据问题 |
| 合成**笔**设备 `CreateSyntheticPointerDevice(PT_PEN)` + `InjectSyntheticPointerInput` | 设备建得出来（`err=0`），帧全部被接受，**系统光标真的一动不动**（实测 `cursorMoved=False`）—— 但微信不产生任何选择（STALE）。悬停优先、`FIRSTBUTTON` 都试了 |
| 合成**触摸**设备 `CreateSyntheticPointerDevice(PT_TOUCH)` | 帧被接受，微信同样不理；而且它**还会把光标带跑**（`cursorMoved=True`），连"不碰光标"这个好处都没有 |

`CreateSyntheticPointerDevice(PT_MOUSE)` 直接 `err=87`，鼠标类型的合成指针根本不给建。

**结论**：微信 4.x 那个自绘窗口（`MMUIRenderSubWindowHW`）只认真实硬件鼠标。
要真的不动光标，只能上内核级虚拟 HID（[vmulti](https://github.com/djpnewton/vmulti) /
[vmulti-mice](https://github.com/Kolyn090/vmulti-mice)）—— 那要编译 2010 年的 WDK 驱动、
自签名、测试模式、装驱动、重启，而且 vmulti-mice 自己的 TODO 里 **Dragging 明确没实现**。
为了拖选去装个未签名内核驱动不划算，所以维持"真实鼠标 + 结束后还原光标"。

### 拉取逼出来的两个窗口状态 bug

**这两个都是"窗口看不见了"导致的，而且互相叠加，症状是"找不到微信"或"切不到前台"：**

1. **`ActivateWeChat()` 只处理最小化，不处理被收进托盘隐藏。**
   托盘状态下 `IsIconic` 是 `false`，`ShowWindow(SwRestore)` 那句根本不执行。
   现在补了 `IsWindowVisible` 检查 + `SW_SHOW`。
   > 这是我自己的锅：早先在拖选收尾加过一句 `Esc` 想清理残留选择状态，
   > 之后窗口就被收进托盘了。实测拖完界面上本来就看不到残留，`Esc` 已去掉。

2. **`FindWeChat()` 依赖 `MainWindowHandle`，而隐藏窗口的这个值是 0。**
   快路径整个失效 → `_wechatHwnd = Zero` → 发送和拉取全废。
   现在加了慢路径：`EnumWindows` 枚举该进程的所有顶层窗口，
   **优先挑"看起来已登录"的**（尺寸够大 + 有 `WS_THICKFRAME`），都不过关才退回"面积最大"。

   为什么不能只按面积挑：微信实测还有第三个 Qt 顶层窗口（`1920x1026`），
   比真的主窗口（`1434x916`）还大，光比面积会挑到它，然后被判成"停在登录界面"。
   日志里能看到这个筛选过程：

   ```
     候选窗口 hwnd=197990    尺寸=1434x916  已登录=是     ← 挑中这个
     候选窗口 hwnd=52827390  尺寸=176x199   已登录=否
     候选窗口 hwnd=197988    尺寸=1920x1026 已登录=否
   found WeChat（窗口被隐藏，走慢路径）: pid=22444 class=Qt51514QWindowIcon 尺寸=1434x916
   ```

## 四个真踩过的 bug

### 1. 全局锁 + 阻塞写 = 整个桥无声哑掉

`WsSend` 原本是这么写的：

```csharp
lock (ClientsLock)                    // 全局锁
{
    s.Write(hdr, 0, hdr.Length);      // 在锁里做网络写
    s.Write(payload, 0, payload.Length);
    s.Flush();
}
```

客户端连接一旦变成死连接（刷新/关闭标签页、半开连接），`s.Write` 会阻塞到 TCP 重传超时。
而 `TcpClient` 默认 `SendTimeout = 0` 表示**无限等**——攥着全局锁的那个线程不放手。
后果：

| 操作 | 结果 |
|---|---|
| `Clients.Add`（注册新客户端） | 卡死 → 新页面收不到 `hello`、收不到任何回执 |
| `Broadcast` / `RemoveClient` | 卡死 |
| HTTP `/status` | **照常应答**（它读 `Clients.Count` 时没加锁） |

症状就是**"桥看着还活着，WebSocket 彻底哑了"**。现场快照是一排 `CLOSE_WAIT`：
浏览器早关了这些连接，桥一个都没处理。

**修法**：`lock (ClientsLock)` → `lock (client)`（只锁单个客户端，锁里绝不做跨客户端的事），
外加 `c.SendTimeout = 3000`，并在收帧处不再用 `catch { }` 静默吞掉 JSON 解析失败。

### 2. `var` 跨 `.then` 不可见的连锁反应

`setPeerPub` 里为了给测试模式留原始密钥字节，写了 `sendRaw = s;`——
而 `s` 是**上一个 `.then` 里的局部变量**，出了那个作用域就没了。
表现是 `ReferenceError: s is not defined`，一点「测试连接」页面就崩。
**`node --check` 完全查不出来**（语法是合法的）。修法是把 `s` / `r` 跟着 promise 一起传出来。

### 3. 端口被占用时崩得很隐晦

`Exception.ToString()` 都会失败，看不到任何有效信息。启动前先确认 8765 空闲——
用 `pretest.py`，它会用**真实 TCP 连接**确认（`Get-NetTCPConnection` 在这台机器上会谎报"空闲"）。

### 4. 防回声判断写成了"内容比较"，把用户的操作也一起吞了

`ClipboardWatcher` 原本是这么防回声的：

```csharp
if (text == _lastSentText) continue;   // do not echo our own paste
```

只要剪贴板内容跟"桥最后一次粘出去的"相同就**永久**忽略。问题是：
用户事后主动 `Ctrl+C` 复制**同一条消息**时，内容当然一样 —— 于是桥一声不响，
页面永远收不到。

真实两端使用时不会撞上（对面的桥没有这条记录），但**单机自测必现**：
测试模式会把"对方的回复密文"也发到微信，你复制回来想看页面能不能解开，
结果什么都不会发生。

**修法**：别比内容，比**剪贴板序号**。

```csharp
// 粘完记住序号
_lastSentText = text;
_lastSentSeq = GetClipboardSequenceNumber();

// 监听循环里：精确识别"这一次变化是我们造成的"
if (now == _lastSentSeq) { _lastSentSeq = 0; _lastSentText = ""; continue; }
if (text == _lastSentText) { _lastSentText = ""; continue; }   // 兜住竞态，且只吞一次
```

两条判据都要：序号那条**精确**；文本那条兜住"序号是粘贴前读的、文本是粘贴后读的"
这个竞态。但文本那条**只能生效一次**——否则又退回成永久忽略。
两条都在日志里留痕（`剪贴板变化 忽略（我们自己刚粘的那一次）`），以后好查。

回归测试 `../test_clipboard_echo.py`（需要桥在跑）：发一条独特文本 →
等桥粘完 → 把**同样的内容**重新写进剪贴板模拟 Ctrl+C → 断言桥推给了网页。

## 为什么不用 UI Automation 读屏

实测过，这条路是死的：

```
window: class='Qt51514QWindowIcon' pid=3100 proc=Weixin
UIA tree:
  [Pane] name=Y(len 21) class=MMUIRenderSubWindowHW
total descendants: 1
Text/ListItem elements: 0
```

微信 4.x 主界面是 **Qt 5.15.14 + 自绘渲染**（`MMUIRenderSubWindowHW` 是它自己的渲染子窗口），
整个窗口对无障碍层**只暴露 1 个元素**，消息文字完全不可见。

所以：读不到 → 只能靠剪贴板。这也正是这套方案**版本无关**的原因。

## 踩过的坑（语言/环境）

- **`csc.exe` 只支持 C# 5**：不能用字符串插值 `$""`、`?.`、`out var`、
  表达式体成员、自动属性初始化器。写的时候要一直记着。
- `GetWindowThreadProcessId` 的第二个参数是 `out uint`，**不能传 `IntPtr.Zero`**。
- 缺 `using System.Diagnostics;`（用了 `Process` 却没引）。
- 短路 `&&` 会让 `out` 的 `RECT` 保持未赋值，报 `CS0170`。
